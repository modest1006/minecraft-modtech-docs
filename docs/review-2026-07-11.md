## 検証済みの指摘（重要度順）

### 1. AssemblerRecipe の `energy` フィールドが実処理で無視されている【Codex 指摘・裏取り済み】

- `AssemblerRecipe` は `energy` を record フィールドに持ち、JSON でも `"energy": 4000` が**必須**（Codec が要求する）。
- しかし `AssemblerControllerBlockEntity.serverTick` は固定値 `ENERGY_PER_TICK(40) × MAX_PROGRESS(100) = 4000` で消費しており、**レシピの energy 値を変えても加工コストが変わらない**。
- 現状サンプルレシピが偶然 4000 なので実害は出ていないが、「レシピごとにコストを変えられる」という設計意図が死んでいる。
- **対処方針**: `serverTick` で `recipe.energy() / MAX_PROGRESS` を per-tick 消費量にする（端数は最終 tick で調整）か、`energy` を optional にして docs から説明を落とす。前者を推奨。

### 2. マルチブロックの Capability 委譲が `isFormed()` を確認していない【Codex 指摘・裏取り済み】

- `ModMultiblock.onRegisterCapabilities` の casing 側委譲は `getController() != null` のみをチェック。
- 通常の形成/解除フローでは `controllerPos` が消えるので問題ないが、**NBT 復元異常・チャンク境界の片側ロード・古いセーブデータ**で「未形成なのに casing が Capability を公開する」余地がある。
- docs の「未形成時は null」という記述と実装が厳密には一致していない。
- **対処方針**: 委譲ラムダに `controller.isFormed()` チェックを追加（1行）。

### 3. Catapult `LaunchHandler` が生成時の `BlockState` を保持している【Codex 指摘・裏取り済み】

- `RegisterCapabilitiesEvent.registerBlock` のプロバイダはクエリ時の `state` を受け取り、`LaunchHandler` がそれをフィールド保持する。
- パイプ MOD が `BlockCapabilityCache` 等でハンドラを**キャッシュ**した場合、その後プレイヤーが POWER を切り替えたり FACING が変わっても**古い状態のまま発射され続ける**可能性がある。
- **対処方針**: `insertItem` 内で `level.getBlockState(pos)` を読み直す（state フィールドを持たない）。

### 4. NBT 復元後にマルチブロック構造を再検証していない【Codex 指摘・裏取り済み】

- `loadAdditional` で `formed`/`members` を復元するが、ロード後に実ブロックが揃っているか再検証しない。
- ワールド編集ツールや部分的なセーブ破損で「ゴースト形成」が残る余地。
- **対処方針**: 初回 serverTick（または `onLoad`）で `formed==true` なら構造再検証、不成立なら `unform()`。

### 5. GameTest カバレッジの穴【Claude/Codex 双方】

現状 4 本（カタパルト初速・ベルコン定常速度・アセンブラ形成・パイプルーティング）は mutation testing で検出力を確認済み。ただし:

- **加工フルサイクル未検証**: レシピマッチ → エネルギー消費 → progress → 入力消費 → 出力生成（最大の穴。指摘1のバグを検出できるテストでもある）
- POWER 0/2 の飛距離、FACING 東以外、`unform()` の後始末、NBT 保存/復元も未カバー。

### 誤検知だった指摘

- **「Java ソースのコメントが文字化けしている」（Codex）**: ファイルは正常な UTF-8。Codex が Windows の cp932 コンソール経由で読んだ際の表示上の問題。`build.gradle` に `options.encoding = 'UTF-8'` 設定済みでビルドも正常。※ Windows 環境の外部ツールは UTF-8 を明示しないと化けて見える、という教訓ではある。

## テスト施策の総括（GameTest 導入）

- **効果**: `runGameTestServer` 約 1.5 秒で機能回帰を検出。BELT_SPEED/SPEED_TABLE の半減 mutation を両方検出できることを実証済み。
- **導入時に得た知見**（詳細は [gametest-setup.md](gametest-setup.md)）:
  - テスト期待値は**実装定数のシンボリック参照にせずリテラル固定**する（参照すると mutation と連動して検出不能になる = tautology）。
  - 理論値より**実測 snapshot** が頑健（block friction 等、物理エンジンの全要素をモデル化するのは割に合わない）。
  - `entity.getX()` 等は**絶対座標**。テンプレ相対で判定するには origin を引く。
- **限界**: 描画（テクスチャ向き・BER・GUI）は原理的に検証不能。ここは runClient での目視が引き続き必要。

## プロセス面の所感

- 「実装 → docs → メモリ → GitHub push」のループは機能している。docs は 12 本になり、実装とほぼ同期。
- **今回のクロスレビュー（Codex）は有効だった**: 自分では「動くから OK」で流していた recipe energy 未使用、stale state、isFormed 未チェックの 3 件は独立した目で見て初めて挙がった。一方で誤検知（文字化け）もあるため、**指摘の裏取りは必須**。
- リモート指示（ユーザー不在時間帯）での開発は「GameTest で機能保証 + 目視項目を帰宅後に絞る」形が定着しつつある。
